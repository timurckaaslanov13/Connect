# Запуск и миграции

Для нового проекта: `docker compose up -d --build --wait`. Каждый сервис ждёт
готовности своей БД и выполняет `alembic upgrade head` перед запуском API.
Данные сохраняются в именованных томах. Порты API по умолчанию 8000–8003,
PostgreSQL 5432–5435, доступны только на localhost. Их можно изменить через
AUTH_PORT, USER_PORT, CHAT_PORT, MESSAGE_PORT и соответствующие *_DB_PORT.

## Уже существующие базы

Начальные миграции предназначены для пустых баз. Если таблицы уже созданы
вручную, не удаляйте тома и не запускайте `downgrade base`: это удаляет таблицы.
Сначала сделайте резервную копию и сравните схему с начальной миграцией.
Только для совпадающей схемы можно отметить исходную версию:

```powershell
docker compose run --rm auth-service alembic stamp 0001
docker compose run --rm user-service alembic stamp 0001
docker compose run --rm chat-service alembic stamp 0001
docker compose run --rm message-service alembic stamp 0001
```

После этого `alembic upgrade head` применит последующие миграции. Если схема
отличается, нужна отдельная миграция переноса; stamp сам не исправляет таблицы.

## Изолированные проверки

Для тестов используйте отдельное имя Compose-проекта (`-p connect-check`) и
другие порты. Не используйте существующие тома проекта для тестов отката.
В тестовой БД проверяются upgrade → check → downgrade base → upgrade → check.
`alembic check` сравнивает актуальную схему с моделями.

## Конфигурация секретов

Перед первым запуском **новых** баз: `python scripts/init_env.py`.
Скрипт создаёт `.env` со случайными ключами и паролями, не выводит их и не
перезаписывает существующий файл. Compose требует заполненные значения.
Для существующих томов скопируйте `.env.example` в `.env`, задайте новые
JWT_SECRET_KEY и INTERNAL_API_KEY (не менее 32 символов), а пароли БД укажите
те, которыми тома были инициализированы. Изменение POSTGRES_PASSWORD в Compose
не меняет пароль пользователя в уже созданной PostgreSQL.

Проверка `/chats/{chat_id}/members/{user_id}/check` теперь требует заголовок
`X-Internal-Token`; ключ доступен только chat-service и message-service.
Недоступность chat-service возвращает HTTP 503, отсутствие членства — 403.

История: `GET /messages/chat/{id}?limit=50&after_id=0`. Ответ — список по
возрастанию ID; для следующей страницы передайте ID последнего сообщения.
Максимальный limit — 100. Пустая страница означает конец текущей истории.

Тестовый стек с отдельной конфигурацией:

```powershell
python scripts/init_env.py --output .env.check --test-ports
docker compose --env-file .env.check -p connect-check up -d --build --wait
python scripts/smoke_test.py --base-port 18000
```

Сквозной тест создаёт новые тестовые аккаунты и сообщения, не удаляя данные.
Миграция уникальности чатов прекращает работу, если в старых данных найдены
дубликаты или личные чаты без двух участников: автоматического удаления или
слияния переписки нет.

## Redis и несколько экземпляров

Compose включает Redis без публикации порта на хост. Message-service использует
Redis Pub/Sub для событий; каждый экземпляр рассылает их своим WebSocket-клиентам.
Без REDIS_URL работает локальная доставка в одном процессе (удобно для тестов).
Pub/Sub не хранит историю: после переподключения клиент должен перечитать её через
HTTP. При сбое публикации сохранённое сообщение остаётся в БД; сервис закрывает
локальные сокеты кодом 1012, чтобы клиент обновил историю. Состояние подписки
проверяется в `/health`. Медленный/сломанный сокет не блокирует остальных навсегда.

Проверка двух экземпляров:

```powershell
docker compose --env-file .env.check -p connect-check -f docker-compose.yml -f docker-compose.check.yml up -d --build --wait
python scripts/smoke_test.py --base-port 18000 --peer-port 18004
```

Дополнительный экземпляр ждёт готовности основного, который применяет миграции.
Для дальнейшего масштабирования миграции следует запускать одним отдельным job.
Реализация Redis использует [официальный asyncio API redis-py](https://redis.readthedocs.io/en/stable/examples/asyncio_examples.html).

## WebSocket-авторизация

URL: `/ws/chats/{chat_id}`, без query-параметра token. После подключения отправьте
первый JSON-фрейм `{"type":"auth","token":"<JWT>"}` в течение 5 секунд.
Сервер проверяет токен и членство, затем отвечает `{"type":"ready","chat_id":1}`.
До ready отправлять сообщения не следует. После ready отправляйте обычный текст.
Закрытие 1008 означает неверный/истёкший токен, отсутствие прав или таймаут входа;
1011 — ошибка зависимостей/сохранения, 1012 — необходимость переподключения,
1013 — медленное или неисправное соединение. После переподключения перечитывайте
историю, устраняя дубликаты по ID. Старый протокол с токеном в URL больше не используется.
Для тестового стека в HTML-странице укажите `ws://127.0.0.1:18003`.

## Все проверки

Установите зависимости message-service в локальное виртуальное окружение, затем:

```powershell
python scripts/test_all.py
python scripts/check_migrations.py --project connect-check
python scripts/smoke_test.py --base-port 18000 --peer-port 18004
```

`check_migrations.py` создаёт отдельную временную БД для каждого сервиса,
проверяет upgrade/check/downgrade/upgrade/check и удаляет только созданную им БД.
Текущие базы сервисов не откатываются. Требуется работающий тестовый Docker-проект.
GitHub Actions выполняет те же проверки на отдельном runner; локально workflow
подготовлен, удалённый прогон начнётся после отправки коммитов в GitHub.
